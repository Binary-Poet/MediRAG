## 5. 首 token 时延对照 —— 真实回退，并发优化回收约一半

**B 组（5 问，每轮 5 问全部作答，n 恒为 5，是唯一可比的样本）**

| 版本 | 三次运行的中位数 | 合并中位数 | vs 基线 |
|---|---|---|---|
| 改前 `f48298c` | 3.21 / 3.27 / 3.48 | **3.27s** | — |
| 改后未优化 `da76892` | 4.19 / 3.66 / 4.17 | **4.17s** | **+0.90s (+28%)** |
| 改后（含并发优化） | 3.71 / 3.79 / 3.63 / 3.58 / 3.79 / 3.82 | **3.75s** | **+0.48s (+15%)** |

三次成对采样的**区间不重叠**（改前 3.21–3.48 全部低于改后 3.63–3.82），因此 +15% 是真实回退而非噪声。

**必须纠正一个中间结论**：优化刚落地时曾以单次采样读到 3.50s vs 基线 3.54s，据此判断「已回到基线」。追加采样后证伪——那次 3.50 是改后侧的幸运快跑撞上改前侧的慢跑。**单次采样的时延对比不构成结论**。

**A 组（n 随落点变化，仅供参考）**：改前 3.36s → 未优化 4.89s → 最终 3.90s。A 组不可比的原因：低置信/急症分支走固定拒答文案、不产生 token 事件，n 在 3–4 之间浮动，且反射轮的长尾把最大拉到 13–14s。

**回退的来源与去向**：

1. 分解使向量/关键词任务数从 2 变为 `子查询数 × 2`，加上图谱路最多 7 个任务。原 `max_workers=3` 硬编码把它们排成多轮、把本应并行的检索串行化。
2. 精排按子查询逐个发起，是**独立的远端网络调用**，串行会把 2–3 次 rerank 时延直接叠加——实测占检索编排的大头。

两处改完后仍余 +15%。这部分**不是可修的开销，是这次改动买来的**：多实体问题确实多做了 2–3 倍的检索扇出。它换到的是 KB-A 0.9963 / KB-C 0.9732 的置信度与逐项对照的回答结构。要消掉它只能减少扇出，那等于取消本特性。

> 口径提示：`fuse` 的并发 rerank 用 `ex.map` 汇总取各子查询 max，与串行逐次 max **语义完全一致**；`retrieve` 的线程池只改 `max_workers`，汇聚顺序仍按子查询下标固定，与线程完成顺序无关。

_TCM_ZHONGFENG = re.compile(r"(太阳|阳明|少阳|太阴|少阴|厥阴)中风|中风(证|表虚)")
def detect_emergency(text: str) -> bool:

## 7. 最重要的一条：分解让反射轮的查询改写失效

### 7.1 怎么发现的

同一问题「如何养生」在改前/改后各跑一次，出现了**相反结果**：改前作答、改后拒答。单次结果无法区分「版本差异」和「反射轮非确定」，于是写了重复采样探针（`.superpowers/.../probe-wellness.py`，每版 5 次），把两者分开：

| 版本 | intent 判定 | n=5 落点 | 最终置信度 |
|---|---|---|---|
| 改前 `f48298c` | `complex` 3 / **`chitchat` 2（抖动）** | 作答 3 / 拒答 2 | 0.3567 – 0.5552 |
| 改后（分解落地，未修反射） | `concept` **5/5 稳定** | 作答 **0** / 拒答 **5** | 0.2631 – 0.2648 |
| 改后 + 本节修复 | `concept` **5/5 稳定** | 作答 **5** / 拒答 **0** | 0.5541 – 0.6597 |

**改前的 `chitchat` 分支正是用户最初报的现象**：`chitchat` 在路由上直接跳到 `safety`，**完全跳过检索**——实测该分支下只有一条 `understand` 步事件，没有任何 retrieve/fuse。这正是「知识库卡在问句理解部分，直接给出未检索到可靠依据」。而它是**抖动的**，所以时好时坏。

### 7.2 根因

拉出两侧的完整步事件对照，反射轮的改写**完全一致**：

```
改前：reflect → rewritten="中医养生方法" → retrieve(13) → rerank confidence=0.5518 → 作答
改后：reflect → rewritten="中医养生方法" → retrieve(13) → rerank confidence=0.2672 → 拒答
```

同一句改写，一次能抬到 0.55，一次纹丝不动。差别在 `fuse`：

```python
queries = [sq["query"] for sq in (state.get("sub_queries") or []) if sq.get("query")] \
    or [state["rewritten_query"]]
```

分解之后，`retrieve` 和 `fuse` 都以 `sub_queries` 为执行单位，**优先读 `sub_queries`，`rewritten_query` 只是兜底**。而 `reflect` 当时只更新 `rewritten_query` —— 于是改写被下游静默忽略，第二轮检索和精排仍在用旧查询「如何养生」。写进去的改写等于白写。

**影响面不止「如何养生」**：所有进入反射轮的问题（低置信 + 无图谱事实）都受影响。这正是例 1/3/5/6 置信度趴在阈值下不动的原因之一。

### 7.3 修复

`reflect` 把改写同时写回 `sub_queries`：

```python
if new_query != state["rewritten_query"] or added:
    names = [e["name"] for e in merged]
    subs = state.get("sub_queries") or []
    if len(subs) <= 1:
        # 单查询（含未拆分的兜底路径）→ 整体替换，与拆分前「改写即生效」语义一致
        upd["sub_queries"] = [{"query": new_query, "entities": names}]
    else:
        # 多子查询（比较/复合）→ 保留按实体的扇出，另把整体改写追加为一条补充查询
        upd["sub_queries"] = [*subs, {"query": new_query, "entities": []}]
```

两个设计决定：

- **多子查询追加而非替换**：替换会抹掉按实体的扇出——那正是本特性存在的理由，且恰好在「比较型问题置信度不足」这个最需要扇出的时刻把它取消。`fuse` 取各子查询精排 max 分，追加只增不损。
- **仅在确有改写/补实体时动它**：LLM 失败回落原文时 `new_query == rewritten_query`，此时不动 `sub_queries`，否则多子查询会被追加一条重复查询。

### 7.4 修复后的「如何养生」实测回答

```

**二、从安神助眠角度** - 酸枣仁养心补肝、宁心安…
```

这是理想形态：**先诚实声明库内没有系统性内容，再把库里确实有的零散内容给出**。既不是改前抖动时那种「直接弹未检索到可靠依据」，也不是硬编造一套养生方案。

## 9. 交付后修正：覆盖度标注 + 文言文转白话

本节记录的是**上面 §3 表格出过的一个错误标记**，以及据此做的两处改动。

### 9.1 先更正 §3 例 4

上面表格里例 4「人参、党参、西洋参……」标的是「正常作答 ✓」。**这个 ✓ 是错的。** 该例拿到
`confidence=0.9626`（全局最高），系统据此显示「证据充分，正常生成」——但演示库里
**只有人参**，党参、西洋参在任何切片、任何图谱节点里都不存在。用户看到的是「三方都比过了」
的假信号，实际只覆盖 1/3。这是交付件里被用户实际撞到的第一个问题。

置信度本身没说谎：`confidence = max(evidence.score)`，衡量的是**证据有多强**，不是**几个实体被覆盖**。
缺的是后一个维度。

### 9.2 覆盖度为什么不能用现成信号推

试过两条路，都不行：

- **`matched_queries`**：它记录「哪些子查询命中了这条切片」。但演示库只有 13 条切片，
  任何子查询都会命中全库，实测每条证据的 `matched_queries` 恒为 `[0,1,2]`——零区分度。
- **复用拒答阈值 `evidence_min_score=0.3`**：第一次实现就是这么写的，实测**直接失效**：
  三个子查询全部 `covered=True`，状态仍是「证据充分」。原因是「党参 补气 功效」这类查询会
  从「人参 大补元气……」切片蹭到 0.44 分——**0.3 对覆盖度毫无区分度**。

所以覆盖度必须保留**每个子查询各自的精排最高分**（`fuse.per_sub`），并用一个更严的阈值判定。

### 9.3 阈值 0.6 是实测出来的，不是拍的

跑真实 `understand → retrieve → fuse`（真 MySQL/Neo4j/精排，脚本
`.superpowers/sdd/2026-09-17-query-decompose-directed-multihop/probe-coverage-threshold.py`），
8 道比较题 / 16 个子查询，逐个核对该实体在库里到底有没有内容：

| 库里确有其内容 | 子查询精排最高分 | | 库里没有（或仅被顺带列名） | 子查询精排最高分 |
|---|---|---|---|---|
| 心脾两虚证 | 0.9916 | | 党参 | 0.4446 |
| 归脾汤 | 0.9963 | | 西洋参 | 0.3695 |
| 四君子汤 | 0.9905 | | 柴胡 | 0.2668 |
| 茯苓 | 0.9841 | | 桂枝汤 | 0.1015 |
| 黄芪 | 0.9731 | | 麻黄汤 | 0.0939 |
| 炙甘草 | 0.9523 | | 逍遥散 | 0.0781 |
| 人参 | 0.9261 | | | |
| 白术 | 0.8536 | | | |

**0.445 ~ 0.854 是空档**，`coverage_min_score = 0.6` 距两侧各留 0.15 以上余量。

两个值得记下的细节：

- **白术 0.8536 判为「有依据」是对的**：白术不是独立切片，但它出现在四君子汤/归脾汤的组成里，
  且查询是「白术 健脾」——那个切片确实在讲健脾并列出白术。而柴胡 0.2668 判为「无依据」也是对的：
  它只在补中益气汤组成里被列了个名，切片里没有任何疏肝内容。精排模型分得开，阈值只是把它固定下来。
- **`coverage_min_score` 与 `evidence_min_score` 必须是两个设置项**：前者看逐子查询（几个实体有依据），
  后者看全局 max（证据够不够强、要不要拒答）。共用一个值就会回到 9.2 的失效状态；调一个也不该动另一个。
  前者不进「推理配置」页——它是内部标定，不是给用户调的旋钮。

### 9.4 落地

- `fuse.py`：保留 `per_sub` 逐子查询分数 → `sub_query_covered`（布尔）+ `sub_query_scores`（原始分）；
  `compare` 且 `0 < covered_n < 查询数` 时状态串改为「部分实体无依据（n/N）」。**置信度不调小**，
  避免误触拒答。
- `context.py`：覆盖不足的实体显式写「（知识库中未检索到与「X」相关的可靠依据）」，
  而不是让该块凭空消失——缺口写明比让模型从「块不存在」去推断更可靠。
- `config.py`：新增 `coverage_min_score = 0.6`，注释里带上面的实测分布。

### 9.5 文言文转白话

用户反馈的第二条：证据原文是文言文（如《金匮要略》「虚劳虚烦不得眠，酸枣仁汤主之」）时
不能原样搬给用户。`answer_cn_tcm.txt` 新增规则 5：必须转述成白话，确需引原文时**先引原文、
紧接着一句白话说明其意**；关键术语首次出现要用白话点明；通俗不得失真（不得增删医理、
不得引入证据外的药材方剂）。

## 10. 已知限制

1. **A 组 7 例的拒答无法区分「编排对但库内无内容」与「编排本身有问题」**——演示库只有 13 切片 / 34 已发布节点。要真正验收 A 组，需要先把这个库补到覆盖麻黄汤、桂枝汤、逍遥散等方剂。
2. **`如何养生` 的作答依赖反射轮**：首轮置信度 0.267 仍低于 0.3 阈值，是靠反射轮改写到 0.55–0.66 才作答。`REFLECT_MAX = 1`，若该轮 LLM 失败或改写无效则仍会拒答——即这条路径的稳定性依赖一次额外 LLM 调用。
3. **时延回退 +15% 是既定代价**，未消除（§5）。
4. **`type=NULL` 的 4 个节点**（另有 5 个 `候选` 状态节点）不参与任何路径模板匹配——模板按 `type` 过滤。
5. **多子查询时反射轮追加的补充查询不参与 compare 证据分组**：它在 `context._evidence_block` 里以 `sq.get("query")` 作标签落到「其他证据」块，不会单独成块。
6. **`coverage_min_score = 0.6` 的标定样本有限**（8 题 / 16 子查询 / 13 切片演示库）。空档看似干净，但库一大、切片一变长，分布就会移动——换语料后应重跑 §9.3 的脚本重新标定，不要当成全局常量。
7. **覆盖度只对 `compare` 生效**：`complex` 等多子查询意图照样记录 `sub_query_covered`，但不改状态、也不在 prompt 里标注缺口。理由是多方面问题缺一个方面与「对比的一方查无此物」性质不同；若实测发现该场景也普遍误导用户，再放开。
